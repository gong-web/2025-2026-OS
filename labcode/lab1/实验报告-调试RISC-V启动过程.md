使用纯软件环境完成对RISC-V的验证，需要一系列模拟器。首先需要一个模拟工具，在X86或ARM的PC上，在Linux开发环境中制造RISC-V运行环境。在实验环境搭建中，有一个模拟器软件，名字叫**QEMU**。它的全称是Quick Emulator，是一个快速对硬件进行模拟的软件。从原理上来说，在设备上创建RISC-V处理器的模拟器，就是针对RISC-V里面的每条指令，执行与之相同的行为。RISC-V有32个寄存器，就在内存中开辟32个变量；RISC-V用二进制程序表示两个寄存器相加，看到这样的二进制编码，就把那两个寄存器对应的内存变量相加后，将结果放到对应地方。以二进制形式逐条指令解析，就可以完成对RISC-V处理器的模拟。

在程序中开辟一片内存，给定一个地址，其实就是一个巨大的数组，对这个数组进行模拟。硬盘和显示器也有类似的模拟方式。QEMU编译好后，会变成系统上的二进制程序，名字叫**qemu-system-riscv64**，这是系统级的模拟，可以完整模拟整个芯片的特权模式和普通用户模式，模拟的是RISC-V 64位。使用这个工具就可以完成对处理器行为的模拟，从而得到这个CPU。

第二件事是得到RISC-V指令的二进制程序。在编程语言课中，有一个重要工具是编译器，包括编译原理课。编译器的功能是把C语言代码编译成计算机可以运行的二进制指令，然后在计算机上运行。从C语言转化成这台计算机的机器语言。现在需要把操作系统的C语言代码转化成在RISC-V处理器上执行的指令，意味着编译器的输出应该是RISC-V的二进制指令。把C语言转换成RISC-V二进制指令，有对应的编译器。在文档前面讲了编译器的下载过程，这里有个专门术语叫**交叉编译**。交叉编译的意思是在X86处理器上运行一个程序，这个程序产生的指令不是X86的，而是RISC-V或ARM的这种情况，叫cross compilation，翻译成中文叫交叉编译器。也就是有一个编译器，本身是X86指令写成的，但产出物不是X86指令，而是RISC-V或ARM指令。

可以直接下载一个交叉编译器。在文档的编译器环节，会说明可以自己做一个交叉编译器，也可以直接下载别人做好的交叉编译器。只要让VSCode找得到它，或者在编译过程中找得到它，就可以用这个下载好的交叉编译器编译在这台计算机上写好的C语言程序，同时得到编译结果是RISC-V的二进制指令。

版本正常的时候，会输出一些提示信息，就知道相关的版本都正确配置好。接下来要做的是追踪整个系统上电的过程，使用QEMU来模拟一个真实的RISC-V处理器是如何上电，以及它的PC如何跳转。需要一个慢动作的观察工具重现这个过程，看得到它在某个时钟周期里在干什么。这时候需要使用到的工具叫**GDB**。GDB是一个单步调试工具，类似于在VSCode里面加断点一步一步向下执行，它不光可以看到断点处的东西，而且可以按照条件指定向后继续执行。GDB可以倒回到上一个状态，只是需要一些特殊的命令。

在CPU一上电的那一瞬间，CPU里面所有的寄存器值都是0，或者都是一个未被初始化的状态，同时内存里所有的东西也都是一个未被初始化的状态。这样就变成了上电那一瞬间系统状态不确定的问题。取到的指令位置取决于**PC**，PC是个寄存器，一上电的时候它是多少？如果不知道，就意味着第一条指令从哪里取过来是不知道的。第二问题就是即便知道了PC的值，由于PC只能从DRAM或内存里取数据，而内存是一个掉电丢失的设备，所以在上电的那一瞬间，内存里什么都没有。所以即便知道了PC的值，仍然不能有效地取到一个指令。在给CPU通电的那一瞬间，到底得到了什么？

有两类存储设备，一类叫**storage**，表现成硬盘、SD卡、U盘，它们是掉电不丢失的。另外一类设备叫**memory**，就像课上讲的内存一样，它不能在掉电的情况下存储数据。在系统上电的那一瞬间，显然需要在某个位置上存储一些数据，确切说是些指令，让CPU在上电的时候就取到那些指令，然后开始后面的执行。第一，它应该是掉电不丢失的；第二，它要在CPU上电的那一瞬间就能够根据PC里的值把它取出来。所以它应该像普通的memory一样，接受load和store这样的指令，把指令取出来的过程。这是一个存储设备，但是它的读取接口跟memory是一样的，所以用load和store就可以。

在RISC-V的处理器里边也有类似的东西，这是原来实验室的RISC-V iMatch开发板，上面有一片放着ROM设备的区域，一个很小的**Flash**。下一个问题是把这个memory放到哪里去？这里引用的是80386的处理器手册，这个手册里面有一个很有意思的值。虽然这些都是寄存器，理论上不能存储什么值，一掉电就没有了，但是硬件工程师通过他们的智慧最终保证在上电的那一瞬间，这些寄存器里边有一个固定的值，每次上电永远都是这个值。这个值不见得是0，在80386处理器里那个值是**FFF0**，它是在这样一个位置上的一个值。这个东西意味着这颗CPU在上电的那一瞬间，它会去FFF0那个位置上取一条指令，取过来这条指令之后解码执行这条指令，然后这条指令的最后会有一个下地址寄存器，告诉CPU它的接下来的那条指令在哪个位置上。

需要在主板上焊接一个ROM设备，这个ROM设备里面存储的就是CPU上电之后应该执行的程序。然后把那段程序的首地址，也就是这一段代码的第一条指令，正好编址编在FFF0这个位置上。于是CPU一上电就会向这个地址发出一个取址的操作，而这个取址的操作的后端正好放着一个read only memory，它可以接收取址的操作，于是它把这个地方的操作返回一个已然预设在read only memory里边的那条指令。这条指令就被CPU得到了，CPU解码，这条指令就可以完成整个后续指令的执行。

Windows操作系统装在磁盘上，那么这一段代码就是教CPU怎么从磁盘上把Windows读进内存里来，然后再跳转到那个位置上去，Windows就开始运行，所以它是个二进制的加载器。除了图上描述的CPU、RAM和Hardware之外，还有一个**ROM**，CPU上电的时候先从ROM里边取指令，ROM里边的这些指令用来帮助CPU从硬盘里把数据挪到RAM。然后这个指令的结尾处最终将PC跳转到这个RAM。那这个ROM有一个特殊的专用名字，在笔记本电脑或台式机里面它叫**BIOS**。

用RISC-V模拟出来的那个处理器设备，它的布局是什么样子的？如果对它的布局感兴趣，可以从QEMU的源代码里面找得到。这是刚才下载的QEMU的源代码，在Hardware RISC-V Virt这个源代码里面就描述了用QEMU模拟出来的RISC-V处理器的内存空间，被QEMU模拟出来的RISC-V处理器的那台计算机的资源配置，能看到这个资源里面它对应到的内存布局都在什么位置上。在整个系统启动的过程当中，RISC-V的处理器会首先跳转到一个内部的上电地址上，然后从那个上电地址再转到一个**OpenSBI**所在的那个位置上，然后由OpenSBI所在的那个位置上逐条去执行指令。执行到最后的时候，OpenSBI再把运行权交转给自己写好的那个操作系统。就像刚才讲到的故事里面，由CPU先交转给BIOS，BIOS把Windows从磁盘里加载在内存里，然后再把PC跳转到内存里。

同学们编写的muCode内核是用QEMU的命令手动的加载在内存的某个固定的位置上。这一次实验就希望同学们利用GDB这个工具来追踪并验证讲述的这个RISC-V处理器上电的过程，它的PC值先被跳转到一个内部的位置，再被跳转到一个由处理器设定好的位置，那个位置里面是就像X86上的BIOS一样的，在RISC-V里面的那个SBI的指令，那一部分的指令再将运行权限交转给80200000所在的那个操作系统指定的那块位置上，然后同学们去看一下那个运行过程的执行。这里面有一个可能还不太容易理解的地方，对于muCode内核而言，它只能被加载在**80200000**这块地址空间，因为只有这里有内存，所以就需要人为控制编译器把所有的代码都挪到这个位置上。

## 知识点

**1.内核栈：**

 **内核栈**是操作系统内核在运行过程中使用的一块内存区域，用于存储函数调用时的局部变量、函数参数和返回地址等信息。它是一个栈结构，遵循先进后出的原则。在引导过程中，bootloader是操作系统内核的启动程序，负责将操作系统加载到内存中并启动它。 bootloader在启动操作系统内核之前会初始化内核栈，并将控制权交给内核。内核栈在引导过程中的作用是提供一个存储空间，用于保存内核在运行过程中的临时数据。当操作系统内核被启动后，它会使用内核栈来执行各种操作，如处理中断、调度任务、处理系统调用等。因此，内核栈是操作系统内核的重要组成部分，它与bootloader的关系是bootloader负责初始化内核栈并启动内核，而内核则通过内核栈来执行各种操作。

**2.固件(firmware)**

 **固件(firmware)是一种特定的计算机软件，它为设备的特定硬件提供低级控制，也可以进一步加载其他软件。固件可以为设备更复杂的软件（如操作系统）提供标准化的操作环境。对于不太复杂的设备，固件可以直接充当设备的完整操作系统，执行所有控制、监视和数据操作功能。 在基于 x86 的计算机系统中, BIOS 或 UEFI 是固件；在基于 riscv 的计算机系统中，OpenSBI 是固件。OpenSBI运行在M态（M-mode）**，因为固件需要直接访问硬件。

**3.地址相关代码与地址无关代码:**

地址无关代码（Position-Independent Code, PIC）和地址相关代码（Position-Dependent Code, PDC）是两种不同的代码类型，其主要区别在于代码中是否包含硬编码的内存地址。

**地址无关代码 (PIC)**:

- **含义**: 这种代码类型不依赖于固定的内存地址，可以在不同的内存位置加载和运行而不需要修改其本身代码。

- **特点**:

  使用相对寻址或寄存器间接寻址，避免了硬编码的内存地址。

  可以被加载到任意内存位置，而无需重定位（relocation）。

  通常用于共享库（shared libraries）或可执行文件，使得共享库可以在内存中的不同位置加载，同时可以减少不同程序的内存占用。

**地址相关代码 (PDC)**:

- **含义**: 这种代码类型包含了硬编码的内存地址，依赖于特定的内存布局。如果将其加载到不同的内存地址，可能会导致错误或崩溃。

- **特点**:

  包含直接使用内存地址的指令或数据。

  在加载到不同的内存位置时，可能需要对其进行重定位，修改内部的地址值。

  通常用于独立的可执行文件，对于每个程序，其被加载到内存的特定位置。

**区分总结**:

- **PIC**:

  不依赖于特定的内存地址。

  使用相对寻址或寄存器间接寻址。

  适用于共享库等场景。

- **PDC**:

  依赖于特定的内存地址。

  使用绝对寻址。

  适用于独立的可执行文件。

### Bootloader

- Bootloader的定义：它是一个小型程序，负责在设备开机时初始化硬件，加载操作系统与引导系统到内存中，并转交控制权给操作系统。

- Bootloader的基本功能：
  1. 硬件初始化：设置处理器和外设，配置内存，准备系统运行。
  2. 加载操作系统：从指定的存储介质（如硬盘、闪存等）中读取操作系统映像，将其加载到内存中。
  3. 转交控制权：完成内核加载后，将执行权转交给内核。

在QEMU模拟的riscv计算机里，我们使用QEMU自带的bootloader: OpenSBI固件，它是 RISC-V 生态系统中的一个开源软件包，提供了一个标准的接口，用于在 RISC-V 处理器上实现超级用户模式和特权操作。

本次实验中，在 Qemu 开始执行任何指令之前，作为 bootloader 的 OpenSBI.bin 被加载到物理内存以物理地址 `0x80000000` 开头的区域上，同时内核镜像 os.bin 被加载到以物理地址 `0x80200000` 开头的区域上。

在计算机中，固件(firmware)是一种特定的计算机软件，它为设备的特定硬件提供低级控制，也可以进一步加载其他软件。

#### 复位地址

复位地址指的是CPU在上电的时候，或者按下复位键的时候，PC被赋的初始值。

##### RISC-V 架构中的复位地址

在 RISC-V 架构中，允许芯片的实现者自主选择复位地址复位地址，通常是 `0x80000000` 或 `0x00000000`，具体取决于系统的配置和实现。在此实验中，QEMU模拟的riscv处理器复位地址为`0x1000`

## 实验原理

### RISC-V 处理器复位与初始状态

- 物理硬件（或 QEMU 模拟器）上电/复位后，硬件把 PC 设置为一个“复位向量地址”（reset vector）。
- 在 QEMU `virt` 平台上（带默认 OpenSBI firmware），该复位地址是 **0x1000**（这是 OpenSBI 前置跳板的一段极小 stub 放置的位置）。
- 此时处理器处于 **M-mode（Machine Mode）**，是特权层级中权限最高的模式，拥有全部 CSR 访问权。
- 复位后常见寄存器状态：
  - `mstatus`：被硬件清理到一个初始安全值
  - `mhartid`：硬件线程（hart）编号寄存器，可被 `csrr a0, mhartid` 读取
  - 内存管理未启用（未分页、无 SATP 配置），所以所有访问都是物理地址
  - 中断默认关闭（需要后续固件配置）

### QEMU virt 机器的关键内存布局（典型）

| 区域             | 典型地址                                  | 用途 |
| ---------------- | ----------------------------------------- | ---- |
| 0x00001000       | OpenSBI 引导 stub（复位向量）             |      |
| 0x00002000 - ... | OpenSBI 主体固件（.text/.data）           |      |
| 0x80000000       | DRAM 起始物理地址（QEMU virt 默认）       |      |
| 0x80200000       | 你自己的内核被加载/链接的起始地址（约定） |      |
| 设备 MMIO        | 0x10000000 起（UART, PLIC 等）            |      |
| DTB (设备树)     | 高地址某个区域（QEMU 动态放置并传递地址） |      |

说明：

- 0x80000000 是“RAM 基地址”。OpenSBI 自身也放在低端物理地址（内建 firmware 映像映射），之后你的内核被放到“RAM 基址 + 偏移”即 0x80200000。
- 0x80200000 的选择：方便把前面部分留给 OpenSBI 或后续 Boot 代码，且对齐页边界（2MB 或 4KB）有利。

### OpenSBI 的角色与价值

OpenSBI 是一个 RISC-V 规范中定义的“Supervisor Binary Interface” 的固件实现，它位于 M-mode，向上为 S-mode OS（你的内核）提供统一抽象：

- 负责早期硬件初始化：定时器、中断控制、串口、PMP（物理内存保护）条目、核间启动（多核时）等
- 规范化 SBI 调用接口（`ecall` 进入 M-mode，由 OpenSBI 实现服务）
- 准备好内核启动所需的启动参数：
  - a0 = hartid
  - a1 = FDT（Flattened Device Tree，设备树起始物理地址）

其核心使命：把一颗“裸”的 M-mode 机器转交给可运行在 S-mode 的通用内核（你当前就是一个最小内核）。

### 为什么最终内核入口是 0x80200000？

- 链接脚本（`kernel.ld` / `boot.ld`）指定起始虚/物理地址，使内核各段（.text/.rodata/.bss）按固定偏移组织。
- 启动时尚未开启分页，地址解释为物理地址（后续如果要做虚拟内存，会在进入内核后建立页表，再打开 `satp`）。
- 0x80200000 留出一小段空间给潜在的 boot code / OpenSBI 使用（虽然现在并未占满，但约定俗成，便于兼容别的教程或工具）。

| 方式                                | 行为                                                | 特点                          | 在本实验的影响                                         |
| ----------------------------------- | --------------------------------------------------- | ----------------------------- | ------------------------------------------------------ |
| `-device loader,file=...,addr=ADDR` | 直接把文件镜像搬到内存物理地址                      | 不经过 OpenSBI 的“加载逻辑”   | 需要你自己确保入口与跳转设置，某些参数传递细节可能不同 |
| `-kernel <file>`                    | QEMU + OpenSBI 认为它是一个“内核映像”并协助准备参数 | 符合标准流程，自动 a0/a1 赋值 | 推荐，用来观察标准引导链路                             |

因此在教学/复现实验中，用 `-kernel` 更贴近现实 OS 引导行为。

### 内核入口代码（`entry.S` / `kern_entry`）作用解析

反汇编（实测）前几条：

典型功能：

1. 设置启动栈（有的实现用 `la sp, bootstacktop`，由链接脚本导出符号）
2. 清空 BSS（`memset` 或手写循环）
3. 准备全局数据区 / 调用 C 级 `init` 函数
4. 进入 `kern_init()` (C 语言)，开始更高层抽象的初始化（打印、内存检测、后续分页建立等）

你日志里 `jal ra, <memset>` 加上后续地址偏移，就是在清零全局未初始化区。

### a0 / a1 语义与后续使用

| 寄存器 | 值                                                   | 意义                                     |
| ------ | ---------------------------------------------------- | ---------------------------------------- |
| a0     | hartid（本实验为 0）                                 | 哪个硬件线程在启动                       |
| a1     | 设备树 (DTB) 地址（实测 0x8f000000 / 0x87000000 等） | OS 可解析硬件拓扑、内存大小、设备信息    |
| sp     | 启动栈顶                                             | 为 C 运行环境提供初始栈帧                |
| ra     | 从上一层（OpenSBI）返回的存根地址                    | 若内核直接返回会跳回（但 OS 不会这么做） |
| t0     | 在引导 stub 用过；进入内核后可重用                   | 不再保留最初 OpenSBI 入口值              |

你的内核如果后续需要枚举设备/内存区间，应解析 a1 指向的 DTB（可用现成解析函数或简单手写遍历结构）。

### M-mode → S-mode 的过渡

- OpenSBI 自身在 M-mode
- 它设置 PMP/PTE 或必要的中断委托，把后续运行环境降低到 S-mode
- 跳转时切换 `mstatus.MPP` → S 并执行 `mret`（或通过汇编逻辑）
- 内核此时已在 S-mode（Supervisior 模式），拥有较高权限但不能直接访问某些机器级 CSR
- 后续访问 SBI 服务需通过 `ecall` 触发陷入 M-mode 由 OpenSBI 处理（例如设置定时器、中断控制等）

### 观察日志中的“现象”与“原理”的对应表

| 日志现象                       | 原理解释                                               |
| ------------------------------ | ------------------------------------------------------ |
| PC=0x1000, 指令 `auipc t0,0x0` | 位置无关基址获取                                       |
| t0=0x80000000                  | 已从数据表装载跳转目标（OpenSBI 主体入口）             |
| a1=0x8f000000                  | QEMU 提供的 DTB 地址（随运行可能变化）                 |
| 断点命中 0x80200000            | OpenSBI 完成初始化并跳入内核                           |
| 内核第一条 `auipc sp,0x3`      | 利用 PC 相对方式定位栈符号（或链接脚本支持的伪装地址） |
| 调用 `memset`                  | 清空 BSS/初始化内存段                                  |
| ra=OpenSBI 某地址              | 标记“上层调用点”，一般不会再返回                       |

## 一句话总括

启动链路的核心逻辑是：复位 stub 利用 PC 相对取参数 → 准备 hartid/DTB → 跳入 OpenSBI 完成 M-mode 初始化 → 设置 S-mode 入场上下文与栈/参数 → 跳到 0x80200000 执行你的内核第一条指令。

## 调试过程与观察

### 阶段一：复位地址初始化（0x1000）

**调试命令**：
```gdb
# 查看当前 PC（程序计数器）的值
info registers pc

# 查看当前位置的汇编指令
x/10i $pc

# 单步执行
si
```

**观察结果**：

CPU 加电后的初始执行地址（实测）：**0x1000**

在上图中可以看到RISC-V计算机加点开始启动**首先停在了`0x1000`处(即程序计数器PC首先被初始化为0x1000)**，这是**因为实际上RISC-V计算机上电时，第一件做的事其实是复位**。复位通常是指**将计算机系统的各个组件（包括处理器、内存、设备等）置于初始状态，并且会启动Bootloader。而QEMU模拟的这款riscv处理器的复位地址**是0x1000，而不是0x80000000。因此首先停在了这个位置上。

在 0x1000 地址处的指令：
```
0x1000:    auipc   t0, 0x0
0x1004:    addi    a2, t0, 40
0x1008:    csrr    a0, mhartid
0x100c:    ld      a1, 32(t0)
0x1010:    ld      t0, 24(t0)
0x1014:    jr      t0
```

**功能分析**：

1. **0x1000: `auipc t0, 0x0`**
   - 将当前 PC 值（0x1000）加载到寄存器 t0
   - 作用：获取当前代码位置的基地址

2. **0x1004: `addi a2, t0, 40`**
   - 计算地址 t0 + 40，存入 a2
   - 作用：准备参数

3. **0x1008: `csrr a0, mhartid`**
   - 读取 mhartid CSR（控制状态寄存器）
   - 作用：获取当前硬件线程 ID（hart ID）

4. **0x100c: `ld a1, 32(t0)`**
   - 从地址 t0 + 32 加载数据到 a1
   - 作用：加载设备树（DTB）地址

5. **0x1010: `ld t0, 24(t0)`**
   - 从地址 t0 + 24 加载数据到 t0
   - 作用：加载 OpenSBI 固件的跳转地址

6. **0x1014: `jr t0`**
   - 跳转到 t0 寄存器中的地址
   - 作用：跳转到 OpenSBI 固件入口点

**查看跳转目标地址**：
```gdb
# 执行到跳转指令前
si
si
si
si
# 查看 t0 的值
info registers t0
```

实测中 `t0 = 0x80000000`，与预期一致（OpenSBI 固件 M 模式入口）。

**这些便是RISC-V硬件加电后的几条指令的一部分，由固化在 Qemu 内的一小段汇编程序负责，首先位于物理地址0x1000处。用于在 RISC-V 架构中进行程序控制和加载还有Bootloader的启动**，例如设置寄存器的值，跳转到指定地址，以及处理特殊情况。其中 `unimp` 表示未实现的指令。

接下来我们通过`si`命令逐行调试，最后通过`jr t0`跳转到物理地址 0x80000000 对应的指令处即启动Bootloader，并进入第二阶段。

### 2.2 阶段二：OpenSBI 固件初始化（0x80000000）

执行 `jr t0` 后，程序会跳转到 OpenSBI 固件。

**调试命令**：
```gdb
# 继续执行到跳转

# 查看当前位置
x/10i $pc

# 查看 OpenSBI 启动信息（需要继续执行一段时间）

```

**OpenSBI 主要功能**：

1. **硬件初始化**
   - 初始化各种 CSR 寄存器
   - 设置机器模式（M-mode）环境
   - 配置中断和异常处理

2. **平台检测**
   - 检测 CPU 核心数量
   - 读取设备树（DTB）
   - 识别硬件特性

3. **内存初始化**
   - 设置物理内存保护（PMP）
   - 配置内存布局

4. **内核加载准备**
   - 将内核镜像放置在 0x80200000
   - 准备跳转到内核的参数（hart ID、DTB 地址）

## 三、实验问题回答

### 问题1：RISC-V 硬件加电后最初执行的几条指令位于什么地址？

**答案**：**0x1000**

这是 RISC-V QEMU virt 机器的复位向量地址。CPU 加电后，程序计数器（PC）被初始化为 0x1000，从这个地址开始执行第一条指令。

### 问题2：这些指令主要完成了哪些功能？

**答案**：

这些初始指令（位于 0x1000 - 0x1014，实测与教材一致）完成了以下核心功能：

1. **位置无关代码准备**
   - 使用 `auipc` 获取当前 PC 位置，为后续相对寻址做准备

2. **启动参数准备**
   - 读取 `mhartid` 寄存器获取当前硬件线程 ID
   - 从固定偏移加载设备树（DTB）地址
   - 准备传递给 OpenSBI 的参数

3. **跳转到固件**
   - 从预定位置加载 OpenSBI 固件的入口地址（通常是 0x80000000）
   - 执行间接跳转，将控制权转移给 OpenSBI 固件

4. **启动引导链**
   - 这是整个启动流程的第一环，后续会由 OpenSBI 完成更多初始化工作
   - 最终 OpenSBI 会跳转到 0x80200000，启动操作系统内核

**完整启动流程总结（实测加强版）**：

```
0x1000 (复位向量)
    ↓
    ├─ 获取基地址和参数
    ├─ 读取 hart ID
    ├─ 加载 DTB 地址
    └─ 跳转到 OpenSBI (0x80000000)
        ↓
        ├─ 硬件初始化
        ├─ CSR 配置
        ├─ 中断设置
        ├─ 内核加载 (到 0x80200000)
        └─ 跳转到内核 (0x80200000)
            ↓
            操作系统内核开始执行
```

#### **回答问题1：最初几条指令的地址**

**答案**：RISC-V 硬件加电后最初执行的指令位于 **0x1000** 地址。

这个地址是 QEMU `virt` 平台定义的**复位向量（Reset Vector）**，硬件/模拟器在上电或复位时会将 PC（程序计数器）设置为这个固定地址。

#### **回答问题2：这些指令的主要功能**

这几条指令构成了一个**最小化的引导桩（Boot Stub）**，主要完成以下功能：

1. **位置无关代码设计**
   - 使用 `auipc` 获取当前 PC 作为基地址，避免硬编码绝对地址
   - 通过相对偏移访问数据表（存储 OpenSBI 入口和 DTB 地址）

2. **准备启动参数**
   - `a0`：传递 hartid（硬件线程 ID），多核系统中用于区分不同核心
   - `a1`：传递设备树（DTB）地址，包含硬件配置信息

3. **跳转到 OpenSBI 固件**
   - 从数据表加载 OpenSBI 入口地址（0x80000000）到 t0
   - 执行 `jr t0` 跳转，将控制权交给 M-mode 固件

**设计精妙之处**：
- 代码非常精简（仅 5 条有效指令）
- 使用数据表方式存储跳转目标，易于配置和移植
- 符合 RISC-V 启动规范，为后续 OpenSBI 准备好必要参数

### 5.5 阶段二：OpenSBI 固件执行（0x80000000）

执行 `jr t0` 后，程序跳转到 **0x80000000**，进入 OpenSBI 固件。

**查看 OpenSBI 入口指令**：
```gdb
(gdb) x/6i 0x80000000
```

**实际输出**：
```
=> 0x80000000:  csrr    a6,mhartid
   0x80000004:  bgtz    a6,0x80000108
   0x80000008:  auipc   t0,0x0
   0x8000000c:  addi    t0,t0,1032
   0x80000010:  auipc   t1,0x0
   0x80000014:  addi    t1,t1,-16
```

**OpenSBI 主要工作**：
1. **M-mode 初始化**：配置机器级 CSR 寄存器
2. **硬件初始化**：设置中断控制器、定时器、串口等外设
3. **多核启动**：唤醒其他硬件线程（如果是多核系统）
4. **准备 S-mode 环境**：设置页表基址、中断委托等
5. **加载内核**：将内核镜像加载到 0x80200000（QEMU 已预加载）
6. **切换特权级**：从 M-mode 切换到 S-mode
7. **跳转到内核**：执行 `mret` 或直接跳转到 0x80200000

### 5.6 阶段三：到达内核入口（0x80200000）

#### 设置断点并继续执行

```gdb
(gdb) b *0x80200000
Breakpoint 1 at 0x80200000: file kern/init/entry.S, line 7.
(gdb) continue
```

**断点命中输出**：
```
Breakpoint 1, kern_entry () at kern/init/entry.S:7
7       la sp, bootstacktop
```

#### 查看内核入口点状态

```gdb
(gdb) info registers pc t0 a0 a1 sp ra
```

**实际输出**：
```
pc             0x80200000       0x80200000 <kern_entry>
t0             0x80200000       2149580800
a0             0x0              0             # hartid
a1             0x82200000       2183135232    # DTB地址
sp             0x8001bd80       0x8001bd80
ra             0x80000a02       0x80000a02    # OpenSBI返回地址
```

**关键寄存器说明**：
- **pc = 0x80200000**：成功到达内核入口点
- **a0 = 0**：主核（hart 0）启动
- **a1 = 0x82200000**：设备树（DTB）物理地址，内核可通过解析获取硬件信息
- **sp = 0x8001bd80**：OpenSBI 设置的临时栈（即将被内核替换）
- **ra = 0x80000a02**：理论返回地址（实际内核不会返回）

#### 查看内核入口处的指令

```gdb
(gdb) x/16i 0x80200000
```

**实际输出**：
```
=> 0x80200000 <kern_entry>:         auipc   sp,0x3
   0x80200004 <kern_entry+4>:       mv      sp,sp
   0x80200008 <kern_entry+8>:       j       0x8020000a <kern_init>
   0x8020000a <kern_init>:          auipc   a0,0x3
   0x8020000e <kern_init+4>:        addi    a0,a0,-2
   0x80200012 <kern_init+8>:        auipc   a2,0x3
   0x80200016 <kern_init+12>:       addi    a2,a2,-10
   0x8020001a <kern_init+16>:       addi    sp,sp,-16
   0x8020001c <kern_init+18>:       li      a1,0
   0x8020001e <kern_init+20>:       sub     a2,a2,a0
   0x80200020 <kern_init+22>:       sd      ra,8(sp)
   0x80200022 <kern_init+24>:       jal     ra,0x802004b6 <memset>
   0x80200026 <kern_init+28>:       auipc   a1,0x0
   0x8020002a <kern_init+32>:       addi    a1,a1,1186
   0x8020002e <kern_init+36>:       auipc   a0,0x0
   0x80200032 <kern_init+40>:       addi    a0,a0,1210
```

**内核入口代码分析**（entry.S）：
```assembly
kern_entry:
    auipc   sp, 0x3              # 计算栈顶地址（相对 PC）
    mv      sp, sp               # 无操作（可能是占位符）
    j       kern_init            # 跳转到 C 语言初始化函数
```

**kern_init 函数开始**：
1. 设置 BSS 段清零参数（a0=起始地址, a2=长度）
2. 调用 `memset` 清零未初始化数据段
3. 准备打印字符串参数
4. 后续会调用 `cprintf` 输出欢迎信息

### 5.7 实验关键数据总结

| 阶段 | 地址       | 关键操作                     | 寄存器状态                                  |
|------|-----------|------------------------------|-------------------------------------------|
| 复位 | 0x1000    | 准备参数并跳转到 OpenSBI      | t0=0x80000000, a0=0, a1=0x1020           |
| 固件 | 0x80000000| M-mode 初始化，加载内核       | 执行大量初始化代码                         |
| 内核 | 0x80200000| S-mode 执行内核初始化         | a0=0(hartid), a1=0x82200000(DTB), sp设置 |

### 5.8 启动流程时序图

```
[上电/复位]
    ↓ PC=0x1000
[复位向量桩代码]
  - 获取基地址
  - 读取 hartid → a0
  - 准备 DTB 地址 → a1
  - 加载 OpenSBI 入口 → t0
    ↓ jr t0
[OpenSBI 固件] (M-mode)
  - 硬件初始化
  - 中断/定时器配置
  - 切换到 S-mode
  - 设置内核参数
    ↓ mret / 跳转
[内核入口 0x80200000] (S-mode)
  - 设置内核栈
  - 清零 BSS
  - 调用 kern_init()
    ↓
[操作系统运行]
```

## 六、拓展内容：现代笔记本的启动流程

在我们通过 QEMU 模拟的 RISC-V 开发板学习操作系统启动过程时，你可能会好奇：**我们日常使用的笔记本电脑又是如何启动的呢？**虽然底层架构不同（x86 vs RISC-V），但核心思想惊人地相似，都是一个从底层固件到高级操作系统的"接力"过程。

### 6.1 现代 x86 笔记本启动流程

现代笔记本的启动流程可以概括为一个精致的**引导链条**：

#### 第一棒：固件（UEFI/BIOS）

当你按下电源键，CPU 的第一条指令并非来自硬盘上的 Windows 或 Linux，而是来自**主板上的一块芯片**——其中存储着 **UEFI 固件**（或传统 BIOS）。

**UEFI 的职责**：
1. **POST（Power-On Self-Test）**：上电自检
   - 检测 CPU、内存、显卡等硬件是否正常
   - 初始化基本硬件（芯片组、内存控制器）
   
2. **硬件枚举与初始化**
   - 扫描 PCI/PCIe 设备
   - 初始化存储控制器（SATA/NVMe）
   - 配置中断控制器（APIC）

3. **引导设备选择**
   - 按照启动顺序（Boot Order）查找引导设备
   - 读取硬盘的 **EFI 系统分区（ESP）**

#### 第二棒：引导加载程序（Bootloader）

UEFI 在硬盘的特殊分区（ESP，通常是 FAT32 格式）里查找并运行**引导加载程序**：

- **Windows**：Windows Boot Manager (`bootmgfw.efi`)
- **Linux**：GRUB 2 (`grubx64.efi`) 或 systemd-boot
- **macOS**：boot.efi

**Bootloader 的职责**：
1. **显示启动菜单**（如 GRUB 的多系统选择界面）
2. **加载操作系统内核**
   - 从硬盘读取内核镜像（如 Linux 的 `vmlinuz`）
   - 加载初始化内存盘（initramfs/initrd）
3. **准备内核参数**
   - 传递设备树或 ACPI 表
   - 传递命令行参数（如 `root=/dev/sda1`）
4. **切换到保护模式/长模式**（x86 特定）
5. **跳转到内核入口点**

#### 第三棒：操作系统内核

引导程序跳转到内核后，操作系统开始接管：

1. **内核初始化**
   - 设置虚拟内存（页表）
   - 初始化调度器
   - 加载设备驱动
   
2. **挂载根文件系统**
   - 使用 initramfs 中的临时驱动
   - 切换到真实的根分区

3. **启动 init 进程**
   - systemd（现代 Linux）
   - System（Windows NT 内核）
   - launchd（macOS）

4. **用户空间启动**
   - 启动系统服务
   - 加载图形界面（X11/Wayland/Windows DWM）
   - 最终呈现登录界面

### 6.2 与 RISC-V 启动流程的对比

| 阶段       | RISC-V（本实验）          | x86 笔记本                    | 共同点                       |
|-----------|--------------------------|------------------------------|------------------------------|
| **固件**   | OpenSBI（0x1000→0x80000000）| UEFI/BIOS（0xFFFFFFF0）      | 都负责硬件初始化和参数传递     |
| **引导**   | QEMU 直接加载内核到 0x80200000 | GRUB/Windows Boot Manager    | 都需要定位并加载内核镜像      |
| **内核**   | uCore（S-mode）          | Linux/Windows（Ring 0）      | 都从特定入口点开始执行        |
| **接口**   | SBI 调用（ecall）         | ACPI/UEFI Runtime Services   | 都提供硬件抽象接口            |

### 6.3 关键相似之处

无论是 RISC-V 还是 x86，启动流程的核心都是**层层递进、分工协作**：

1. **固件（本能层）**
   - RISC-V：OpenSBI
   - x86：UEFI
   - **作用**：最基础的硬件唤醒，像电脑的"本能"

2. **引导程序（搬运工）**
   - RISC-V：QEMU 帮忙预加载（真实硬件需要 U-Boot 等）
   - x86：GRUB/Windows Boot Manager
   - **作用**：找到并加载操作系统内核

3. **操作系统（大脑）**
   - RISC-V：uCore/Linux
   - x86：Windows/Linux/macOS
   - **作用**：接管全部控制权，提供用户交互

### 6.4 启动时间对比

| 设备类型        | 典型启动时间 | 瓶颈                     |
|----------------|------------|--------------------------|
| 本实验 QEMU     | < 1 秒      | 模拟速度                  |
| 现代 SSD 笔记本 | 10-20 秒    | 固件初始化 + 驱动加载     |
| 传统 HDD 笔记本 | 30-60 秒    | 磁盘 I/O 速度             |
| 嵌入式设备      | 3-10 秒     | Flash 读取速度            |

### 6.5 安全启动（Secure Boot）

现代笔记本还引入了**安全启动**机制：

- **UEFI Secure Boot**：
  - 固件验证 Bootloader 签名
  - Bootloader 验证内核签名
  - 防止恶意软件在启动阶段植入

- **对应到 RISC-V**：
  - OpenSBI 可以验证内核签名（需要硬件支持）
  - 使用 PMP（物理内存保护）隔离固件和内核

### 6.6 理解启动流程的实用价值

掌握启动流程知识可以帮助你：

1. **故障排查**
   - "卡在 BIOS 界面"：固件层问题
   - "找不到操作系统"：引导程序或分区表损坏
   - "蓝屏/Kernel Panic"：内核或驱动问题

2. **系统定制**
   - 配置 GRUB 多系统启动
   - 修改内核启动参数
   - 制作自定义 Live USB

3. **性能优化**
   - 禁用不必要的固件功能
   - 优化 initramfs 大小
   - 调整启动顺序

### 6.7 小结

这个流程与我们实验中的 QEMU 启动（从 OpenSBI 到内核）本质是一样的，都经历了**"固件 → 引导程序 → 操作系统"的三级跳**。只不过在真实的 PC 中，每一步都更加复杂，涉及更多安全检查和硬件初始化，但其层层递进、分工协作的核心设计哲学是完全共通的。

**理解了这一点，下次开机时你就能感受到，短短几秒的背后，正是一场井然有序的系统交接仪式。**
